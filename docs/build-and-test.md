# Build and test

The repository has no `go.work` and no `replace`, so use `GOWORK=off` when this folder sits inside a Go workspace.

## Checks

```sh
GOWORK=off go vet ./...
GOWORK=off go test -timeout 30m ./...      # about 10 minutes, so go's default limit of 10 is too short; starts an entry node and a pin in the process, on loopback only
GOWORK=off wails3 build
cd frontend && npm test && npm run lint   # the strings, the message groups, the sidebar, the notch page and the window (with Google Chrome)
```

What the main tests cover:

- `TestInviteJoinAndChat` runs three instances with separate data directories. The founder creates an invite, B joins once an admin approves, and C is refused for an invite that is used up, expired, revoked, denied or not a code, then joins with a new invite. Messages flow between the founder and B, including those B misses while it is closed, which come from the pin once, in order.
- `TestProfilesAndRooms` runs three instances (the founder, B and C, joined by invite, with an in-process bootstrap node and pin). B changes its name and the others see it, with the events. The founder adds a room and everybody sees it, and a member that tries gets `ErrNotAdmin`. C is closed while B changes its name again, B puts it on the pin and goes offline, and C opens: it shows the name it kept, then the new name from the pin, with B offline. B cannot write C's profile (its copy is read-only).
- `TestInvitedByAMember`, `TestDirectorySurvivesARestart` and `TestCapabilityCoversBothLogs` cover an invite from a member, the directory in the data directory and the pin capability for both logs. `TestManyActiveInvites` keeps 40 invites active and joins through the last one.
- `pins_test.go` runs two pins: every pin gets the logs, a pin that is down gives a warning and the others still keep the messages, missed messages come from the second pin when the first is gone, a pin that is behind changes nothing, and an invite carries every pin (and is refused by a joiner whose `-max-pins` is lower). `config_test.go` covers the pin list forms (`-pin`, `-pin-file`, the variables), what is refused, the token of each pin and the summary the window gets.
- `entrykeys_test.go` covers the derived entry keys. `TestOfflineSenderIsReadFromThePin` is the main case: B is closed, A sends three messages, changes her name and quits, and B opens with only the pin up and shows all of it; the pin's store holds no entry key, no entry secret and no conversation key. `TestJoinerReadsTheEarlierHistory` covers a joiner that reads what its inviter sent before, and `TestHostileMemberIsSkippedAndMarked` a member whose records commit to other keys: its entries are skipped, it is marked, and the others still show. Unit tests cover the entry secret vector, the refused headers, `Ciphertext` access, a data directory whose log has random entry keys, which is refused and left as it was, a folder that lost `conversation.json`, an entry that waits for its key, a pull held between the pull and the derivation (`TestUnlockRace`), a failed pull that still derives, a failed write that is retried at the next pull, a refused entry in the middle of a log, a hostile directory, a hostile member pulled online that offers its keys, a reader without the conversation key, the quarantine after 256 refusals and its way back (`TestQuarantineWayBack`), and a flood of 65,536 bad entries (`TestHostileFlood`, about 9 s; 512 entries under `-race`, set in `flood_race_test.go`).
- `nopin_test.go` runs `TestConversationWithoutAPin`: an app with no pin creates a conversation (no pin in its `conversation.json`, no `pin-tokens/`, no pin error), invites carry no pin, a joiner without a pin gets the earlier messages from the online founder, members online exchange messages directly, a member who was offline gets what it missed once its sender is online (shown as from a peer), and a member who joins while another is offline gets that member's earlier message only when it is back. `config_test.go` (`TestPinIsOptional`) and `invite_test.go` cover a key with no pin, a pin file that lists nothing, and a grant or `conversation.json` with an empty list of pins. The frontend tests check the no-pin sentences in the three languages and, in a headless Chrome, that the add menu is enabled with no pin and that the sidebar shows one quiet line about it.
- `relay_test.go` covers the connection relays. `TestChatThroughRelay` is the main case: two chats that refuse every incoming connection (a test firewall on kolo-transport, as a strict NAT) and a pin that takes nobody's logs, with an in-process kolo-relay on 127.0.0.1 behind a tap that stands where the relay's operator stands. The invite, the hellos, a message, the history B missed while closed and a name change all arrive through the relay, and the tap's bytes hold no text, name, conversation key, entry secret or entry key. The tap also must see both members' public keys, which a relay operator does see, so a tap that reads the wrong layer fails. `TestStrangerThroughRelayIsRefused` sends two hellos from a stranger's key through the relay: a member's hello replayed (its signed header names another key) and the stranger's own valid headers with a proof made under another conversation key. Both are refused, and the stranger cannot pull. `TestWrongRelayKeyIsReported` and `TestWrongRelayKeyIsReportedToAJoiner` list a relay with another key and check the window (an app with no conversation through the key check at start) and the terminal. `TestRelayRenewalIsNotAFailure` uses a relay whose places last one second: the renewals never show as a failure or a log line. `TestJoinMessagesWithRelays` checks the join sentences with and without relays. Unit tests cover the relay settings (sources, 17 relays from the flags and from a file, bad keys, IPv6 forms, a symlink to a device, a directory, a large or missing file), the 195 s join with relays, the help text and each relay state.
- `state_test.go`, `mux_test.go` and `braid_test.go` cover the member and room lists (see [shared-state.md](shared-state.md)). The apply function goes through `kolobraidtest.CheckApply`, `FindDivergence` and `CheckUpgrade`, with duplicate, unicode, bad and longest names, malformed bodies and a version 2 entry that halts it. The mux routes each tag, cancels a bad or late stream only, keeps a burst of 32 braid streams, closes a stuck braid part only, and ends with the connection. `TestTwoAdminsConverge` has two admins add one room at once and one remove a member while the other approves a new one: every member ends with the same lists. `TestRemovedMemberIsNotTalkedTo` shows what removal does and does not do (the removed member still reads the pin), `TestKeyAloneIsNotMembership` a fresh kolo-id with the key, `TestBraidFaultPausesOnlyTheMemberList` a malformed braid message that pauses the lists and keeps the chat, `TestStuckBraidPausesTheMemberList` a braid reader jammed by streams that never end, and `TestStreamCreditOverRealLinks` 40 streams at once over a swarm and a relayed connection; others cover the restart, the founder's hand over, the bound of 64, the flood of refused entries, dropped events, the halted state, a joiner not listed yet and an offline member. `TestMemberFolderWithoutConversationIsKept` shows that a member's folder that lost `conversation.json` is refused and kept, never taken for an unfinished join. `TestAdmitKeepsOneSettler` checks that approving members never makes a settler or an unapproved admin and writes no Settlers entry.
- `conversations_test.go` covers several conversations in one example, and `TestIdleCostOfSixtyFourConversations` (skipped unless `KOLO_CHAT_MEASURE_64=1`) times and measures 64 engines. `TestConversationsStayApart` is the main case: Alice starts two conversations, which get two folders, kolo-ids and topics; Bob joins both, each message reaches its own conversation only, and with Alice offline Bob reads each from the one pin. Other tests cover the refused data folders of another layout, left as they were (`TestOtherLayoutIsRefused`, `TestOtherLayoutKeepsItsConversations`), the conversation key setting, `-max-conversations`, a fixed `-listen` port, the relay key check once per example (`TestRelayCheckOncePerApp`), Create, a join that fails or is cancelled and starts afresh (`TestFailedJoinStartsAfresh`), a conversation that does not start, unknown IDs, Rename, and the cost of eight conversations, idle and with a braid and 3 peers each (`TestIdleCostOfEightConversations`, which logs it). `TestLeaveOneConversation` (in `leave_test.go`) leaves one of two: only its folder goes, the other still talks, IDs that spell a path remove nothing, and the log holds no key, secret, code, name or text.
- `TestHistoryAfterRestart` restarts B on the same data directory: the window gets the history once, B's own message included, in the order sent, and nothing of it again live. `TestHistoryIsBounded` and `TestHistoryOrder` cover the bound and the merge rule, `TestShownButNotKeptShowsLater` a message shown but not yet kept when the example closed, and `TestHistoryKeepsTheNotchQuiet` that the history is never unread.
- `network_test.go` covers the three ways to choose a network: no `-bootstrap` is the public network (the settings carry no entry node, kolo-swarm uses kolo-dht's built-in list, the example listens beyond loopback, and the payload for the window carries the mode and no address), `-bootstrap` alone is your own network and is used alone, a bad entry is refused, and an unreachable network starts the room offline, asking again by itself, with a `*NetworkError` that names the three options. `TestMain` replaces the call that joins the network, so a test that starts without `-bootstrap` fails instead of sending a packet to a public address: every test here uses an entry node on `127.0.0.1`.
- `notch_test.go` and `tray_test.go` test the notch and the tray with no window.
- `reconnect_test.go` covers staying connected, with real engines on loopback only. `TestFortyRoomsStartGently` starts 40 rooms against an entry node of the test's own that lets one address send 50 requests a second: `Start` returns after the first four, every room ends up online, the room on screen is among the first, the node drops none and the most it gets in any second, while the rooms start and once they are up, stays under the limit (it logs 24 and 15). `TestFortyRoomsAtOnceHitTheLimitAndRecover` starts the same 40 at once, which drops requests, and every room still ends up online by asking again. `TestFailingNetworkRetriesThenRecovers` starts six rooms with no entry node answering: they say offline with no error, keep asking, keep a message typed meanwhile and all connect when the network is back. `TestPeerLostAndNetworkBackDeliversEverythingOnce` cuts the connection between two members and takes the network away: the room says online, reconnecting, offline, `Send` never waits, and after the network returns every message arrives once, in order. `TestEntryNodeDownForTenSeconds` stops the entry node for 10 seconds with a connection cut, and `TestSendWhileThePeerIsGoneIsKept` restarts a member that missed messages. `TestJoinWhileOfflineSaysWhy` joins with no entry node answering: the error names the three ways and the room is offline, not failed. `TestRetryDelay` checks the growing, jittered wait.
- `payloads_test.go` marshals every event payload empty or as it starts, and a joiner's events and methods, and fails on a `null`; `report_test.go` checks that `ReportError` logs one cleaned line cut to its bound. `frontend/src/window.test.js` serves both windows with the mock in a headless Chrome on 127.0.0.1: every list as `null` still shows the window, and an error shows the error pane, which reaches `ReportError` and copies. The same test checks the window as a user sees it: one list of rooms with no inner level, messages grouped by author and by five minutes with day chips, the sidebar folding to a rail and remembering it (also with storage that throws), the add menu and its dialog with the keyboard, Escape, a click outside and the focus going back to the + button, the members panel, a window of 800 and one of 2000 pixels, the public network without addresses, the connection states of a room (a dot in the list, a sentence under its name and a note, never an error) and Leave room. It is skipped without Google Chrome. `groups.test.js` covers the grouping rule and the day labels, `sidebar.test.js` the stored choice and the focus helpers. `cd frontend && node dev/shots.mjs --all <dir>` (with `npx vite --config dev/vite.config.js` running) takes every screen at four sizes in the dark and light themes and fails when a screen scrolls sideways or cuts the newest message.

## Frontend packages

`frontend/package-lock.json` pins every package to an exact version, and the build installs from it with `npm ci`, which never takes a newer one. `frontend/.npmrc` sets `minimum-release-age`, a rule that pnpm and bun honour for a new `install` or `add`; npm has no such setting, warns that it is unknown and ignores it, so with npm the lock file is what keeps a freshly published release out.

## Release files

No CI is needed. On a Mac with Go, Node (npm), the `wails3` CLI and Docker Desktop:

```sh
scripts/release-local.sh            # writes ./dist-release/<version>/
scripts/release-local.sh out-dir    # writes out-dir/<version>/
```

It builds the committed HEAD in a temporary copy, named after `git describe --tags`:

- macOS: a universal `.app` as `.zip` and `.dmg`;
- Windows amd64 and arm64: `.exe`, `.zip` and an NSIS installer;
- Linux amd64 and arm64: `.tar.gz` and `.deb`, built in Ubuntu 24.04 containers (amd64 emulated);
- `SHA256SUMS`.

The version is the git tag (`git describe --tags`). The script passes it to the example with `-ldflags "-X main.version=..."`, so Settings and `AppInfo.version` show it, and `scripts/set-version.sh` writes it into the files that carry one: `build/config.yml`, the macOS `Info.plist`, the Windows manifest, `info.json`, the MSIX files, the NSIS defaults and `nfpm.yaml` (committed with the development version 0.0.0). The script checks that each Windows and Linux binary and the bundle carry it. A build without `-ldflags`, such as `go build` or `wails3 dev`, reports `dev`; `wails3 task package` takes the version from the tag, or `APP_VERSION=0.1.0` on the command line.

The AppImage target downloads linuxdeploy at a pinned release and checks its SHA-256 before it runs it. The Windows uninstaller deletes the files the installer wrote and the folder only if it is empty, since the person may install into a folder that holds other files. The deb names Ciranda as its maintainer and https://kolo.ciranda.dev as its homepage.

The files are not signed with a developer certificate or notarized. `KEEP_IMAGES=1` keeps the Docker build images for the next run.
